# 业务架构与核心规则

> 文档编号：DOC-DESIGN-001  
> 创建日期：2026-08-01  
> 状态：初始设计基线

## 1. 设计原则

- 单实例优先，满足当前学校部署与个人开发者维护能力；
- 数据库保存最终事实，Redis 只保存短期和可重建状态；
- 对外接口优先通过 OpenAPI 设计；
- 选寝提交采用“临时占用 + 数据库最终确认”两阶段业务流程；
- 房间状态通过服务器发送事件推送，但客户端必须能够重新获取权威快照；
- 匹配推荐使用确定性算法，保证可解释、可复现和可测试；
- 个人选择、组队选择和统一随机分配共享同一资格、床位和最终分配约束。

## 2. 总体结构

```text
浏览器
├── 学生端
└── 管理端
        ↓
REST + 服务器发送事件
        ↓
Spring Boot 单体后端
├── 认证与权限
├── 学生与组织
├── 宿舍资源
├── 选寝批次与规则
├── 问卷与匹配
├── 队伍
├── 临时占用与最终分配
├── 随机选择与随机分配
├── 实时推送
├── 导出与统计
└── 审计
        ↓
MySQL + Redis
```

## 3. 后端模块职责

### 3.1 `model`

- 保存 OpenAPI 契约；
- 生成服务端接口和数据传输对象；
- 不保存业务实体和复杂业务逻辑。

### 3.2 `client`

- 生成远程调用客户端；
- 当前单体系统不强制使用；
- 保留作为未来外部系统集成入口。

### 3.3 `server`

- 控制器；
- 应用服务和领域服务；
- 持久层；
- Redis、导出和推送适配；
- 业务校验、事务和审计。

### 3.4 `starter`

- Spring Boot 启动入口；
- 运行配置；
- 依赖组装；
- 健康检查和应用启动。

## 4. 核心数据模型

建议主要实体：

```text
Student 学生
Organization 组织
Campus 校区
DormitoryBuilding 宿舍楼
Floor 楼层
Room 房间
BedFrame 床架
Bed 床位

```

Redis 不对应永久业务实体，建议仅保存：

```text
临时床位占用
房间热点状态缓存
匹配候选缓存
接口频率限制
服务器发送事件连接元数据（仅内存或短期）
```

## 5. 床位模型

床位不能只用“房间剩余数量”表示，必须作为独立资源。

建议字段：

- `bed_id`；
- `room_id`；
- `bed_frame_id`，没有共享床架时可为空；
- `bed_code`；
- `bed_type`；
- `position_index`；
- `enabled`；
- `version`。

床位类型可包括：

```text
LOFT_BED_DESK 上床下桌
BUNK_UPPER 双层床上铺
BUNK_LOWER 双层床下铺
OTHER 其他
```

五人间示例：

```text
Room 501
├── Bed A：LOFT_BED_DESK
├── Bed B：LOFT_BED_DESK
├── Bed C：LOFT_BED_DESK
└── BedFrame D
    ├── Bed D-U：BUNK_UPPER
    └── Bed D-L：BUNK_LOWER
```

## 6. 临时占用设计

### 6.1 Redis 键

建议形式：

```text
dormitory:batch:{batchId}:bed:{bedId}:hold
```

值至少包含：

- 学生编号或队伍编号；
- 随机占用令牌；
- 创建时间；
- 过期时间；
- 占用类型：个人或队伍。

### 6.2 原子申请

个人床位申请可以使用带过期时间的 `SET NX`。组队需要同时占用多个床位，建议使用 Lua 脚本一次检查并写入全部床位，避免只占用部分床位。

错误做法：

```text
先 GET 判断没有占用
→ 再 SET 写入
```

两个请求可能同时通过第一次判断，形成竞态。

### 6.3 释放

释放操作必须比较令牌：

```text
只有 Redis 中的令牌与请求令牌相同，才能删除占用键
```

不能直接根据床位编号删除，否则一个请求可能错误释放另一个学生新获得的占用。

### 6.4 续期

- 是否允许续期由批次配置；
- 只能由原令牌持有者续期；
- 设置最大续期次数；
- 批次结束后不得续期；
- 页面隐藏或断线不应无限续期。

## 7. 最终提交与数据库一致性

建议唯一约束：

```text
同一批次 + 学生：只能有一个有效分配
同一批次 + 床位：只能有一个有效分配
```

最终提交顺序：

```text
校验登录和权限
→ 校验批次状态和时间
→ 校验学生资格与当前状态
→ 校验床位和房间状态
→ 校验 Redis 令牌
→ 开启数据库事务
→ 条件写入最终分配
→ 更新学生与床位业务状态
→ 写入分配历史和审计
→ 提交事务
→ 按令牌释放 Redis
→ 发布房间状态事件
```

数据库写入发生唯一约束冲突时，应返回“床位已被他人确认”等稳定业务错误，并刷新客户端状态。

不能把 Redis 成功占用视为数据库一定提交成功。数据库失败时，占用可以保留短时间供重试，也可以安全释放，具体策略需要在第一阶段详细设计中固定。

## 8. 组队一致性

组队选寝需要整体提交：

- 队伍必须锁定；
- 成员数量与候选床位数量匹配；
- 所有成员都有资格；
- 所有成员均未完成其他分配；
- 所有床位属于同一允许房间或规则允许的范围；
- 多床位临时占用整体成功；
- 最终数据库事务整体写入；
- 任一成员或床位冲突时整体回滚。

建议先由队长选择房间，系统依据成员床位偏好给出房内床位分配建议；成员是否需要逐一确认由批次规则决定。

## 9. 服务器发送事件设计

### 9.1 采用原因

本项目的主要实时需求是服务器向浏览器单向推送房间状态。学生操作仍使用普通 REST 请求。因此服务器发送事件比 WebSocket 更简单：

- 基于 HTTP；
- 浏览器原生支持自动重连；
- 适合单向状态通知；
- 服务端和代理配置较简单；
- 当前不需要浏览器通过长连接持续发送消息。

### 9.2 订阅粒度

按房间推送：

```text
批次 + 房间 → 一组订阅连接
```

不建议把整个学校所有床位放在一个全局连接中，否则消息量和权限控制都会增加。

### 9.3 推送流程

```text
学生打开房间页面
→ REST 获取权威房间快照
→ 建立服务器发送事件连接
→ 服务端发送连接确认和房间版本
→ 床位临时占用、释放或最终分配
→ 服务端发布房间事件
→ 当前房间连接收到事件
→ 前端局部更新或重新获取快照
→ 页面离开时关闭连接
```

### 9.4 事件结构

```json
{
  "eventId": "事件编号",
  "eventType": "BED_HELD",
  "batchId": "批次编号",
  "roomId": "房间编号",
  "bedId": "床位编号",
  "roomVersion": 12,
  "occurredAt": "服务端时间",
  "expiresAt": "临时占用过期时间，可为空"
}
```

推送不应包含占用学生姓名。学生列表和公开标签由有权限的 REST 接口返回。

### 9.5 心跳与重连

- 服务端每隔固定时间发送注释心跳或 `HEARTBEAT`；
- 写入失败时移除连接；
- 页面离开主动关闭；
- 浏览器重连携带最后事件编号；
- 服务端无法补发时发送 `RESYNC_REQUIRED`；
- 前端重新请求快照并建立新连接；
- 单实例中可以使用内存连接注册表，不需要外部消息队列。

## 10. 匹配算法设计

### 10.1 总体流程

```text
问卷答案
→ 特征编码
→ 标准化与权重
→ 硬约束过滤
→ 粗筛候选
→ 精确计算学生/房间匹配分
→ 排序和随机抽样
→ 解释结果
```

### 10.2 特征编码

数值特征示例：

- 入睡时间转换为一天中的分钟并处理跨午夜；
- 起床时间同理；
- 清洁频率转换为每周次数；
- 噪声、睡眠敏感、社交程度使用有序等级。

枚举特征示例：

- 空调温度偏好；
- 是否接受语音游戏；
- 床位类型偏好。

二元关键冲突项可以使用 0/1，但要注意政策和隐私边界。

### 10.3 学生间相似度

可以采用加权距离：

```text
D(a,b) = Σ wi × difference_i(a,b)
S(a,b) = max(0, 1 - D(a,b) / Dmax)
```

其中：

- `wi` 是可配置权重；
- `difference_i` 针对不同特征定义差异；
- 关键冲突项可以使用更高权重或额外惩罚；
- 所有结果限定在统一范围内。

### 10.4 房间匹配分

若房间已有成员集合 `R`：

```text
平均分 = mean(S(student, member))
最低分 = min(S(student, member))
关键冲突惩罚 = penalty(conflicts)
床位偏好分 = bedPreference(student, bed)

房间总分 = α × 平均分
         + β × 最低分
         + γ × 床位偏好分
         - δ × 关键冲突惩罚
```

最低分用于防止“平均看起来很好，但与其中一名室友严重冲突”。空房间可以使用房间标签、批次默认分或与组队成员的内部匹配分。

### 10.5 秒级候选检索

不需要对全部学生和全部房间做全量两两比较：

1. 按批次、性别、校区、楼栋和容量建立硬约束索引；
2. 对主要习惯建立特征桶，例如作息区间、噪声容忍区间；
3. 维护房间成员特征和、人数、中心向量和关键标签；
4. 先取得有限候选房间；
5. 对候选执行精确评分；
6. 取前若干名返回；
7. 房间成员变化后更新聚合特征并失效缓存。

学生随机选择可以在高分候选中进行带权随机，而不是永远返回同一个最高分房间，以兼顾选择多样性和床位均衡。

### 10.6 可解释结果

示例：

```text
匹配度较高：作息时间接近、都偏好安静、卫生频率接近
需要注意：空调温度偏好存在差异
```

不得输出：

```text
你们一定能成为好朋友
该学生性格不好
```

## 11. 随机分配设计

随机分配不是完全无规则抽签。建议分层：

1. 固定本次执行的未分配学生和可用床位快照；
2. 先处理特殊硬约束学生；
3. 处理完整队伍；
4. 按特征桶对学生分组；
5. 使用启发式算法逐步放入房间；
6. 对局部结果进行交换优化，降低严重冲突；
7. 输出无法分配原因；
8. 预演通过后正式写入。

可使用贪心加局部搜索，不需要引入复杂人工智能模型。正式执行应保存算法版本、参数、随机种子和输入摘要，以便复现。

## 12. 错误码方向

建议稳定业务错误类别：

- `BATCH_NOT_OPEN`；
- `BATCH_CLOSED`；
- `STUDENT_NOT_ELIGIBLE`；
- `STUDENT_ALREADY_ASSIGNED`；
- `BED_NOT_AVAILABLE`；
- `BED_HELD_BY_OTHER`；
- `HOLD_EXPIRED`；
- `HOLD_TOKEN_MISMATCH`；
- `TEAM_STATE_CONFLICT`；
- `TEAM_CAPACITY_NOT_ENOUGH`；
- `ALLOCATION_CONFLICT`；
- `REDIS_UNAVAILABLE`；
- `RESYNC_REQUIRED`。

前端根据稳定错误码展示可操作提示，不能依赖后端异常文本判断业务。

## 13. 审计事件

至少记录：

- 批次创建、发布、暂停、关闭和取消；
- 学生资格变化；
- 房间和床位启用状态变化；
- 队伍创建、锁定和解散；
- 临时占用申请结果，可按需要保存摘要而非所有心跳；
- 最终分配创建；
- 随机分配预演和正式执行；
- 人工调整；
- 结果导出。

审计记录不能被普通业务删除。
