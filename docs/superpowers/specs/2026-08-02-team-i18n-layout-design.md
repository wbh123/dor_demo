# 组队确认、国际化与床位拆分设计

## 目标

本次改造同时解决三类问题：

1. 组队邀请在主页和组队页均可处理，队伍选寝只包含已确认成员；
2. 系统提供简体中文和英语切换，管理员分别维护两种语言的新生欢迎语；
3. 宿舍布局编辑器按床具单元展示“上床下桌/上下铺”，将上床下桌切换为上下铺时新增一个独立床位，并同步房型与容量。

## 组队状态规则

- 待处理邀请继续保留在组队页面。
- 学生主页读取待处理邀请，并弹出第一条邀请。学生可接受、拒绝或“暂不确认”。暂不确认只关闭当前页面会话中的弹窗，不修改数据库。
- 队伍成员数量只统计 `JOINED` 或 `LOCKED` 成员，`INVITED` 不计入选寝人数。
- 队长在 `FORMING` 状态即可开始组队选寝。开始前若存在待处理邀请，前端必须展示“未确认邀请将失效”的确认框。
- 后端锁定队伍时原子执行：校验已确认人数、取消全部待处理邀请、将对应邀请成员改为 `REMOVED`、将已加入成员改为 `LOCKED`、队伍改为 `LOCKED`。
- 普通成员可主动退出。队长退出时队伍解散，所有未完成分配的成员恢复为可个人选寝状态。
- 学生进入个人选寝列表前，如果处于有效队伍中，前端必须展示退队确认。确认后调用后端退队接口，再加载个人房间列表。
- 已完成床位分配的队伍或成员不能退出或切换到个人选寝。

## 国际化规则

- 首期语言为 `zh-CN` 和 `en-US`。
- 语言状态由前端全局模块管理，并保存到浏览器本地存储；默认根据浏览器语言选择，无法识别时使用简体中文。
- 应用外壳提供语言下拉框，学生与管理员所有页面共用同一语言状态。
- 前端固定文本、状态名称、按钮、表单提示和常见错误通过翻译键获取。
- 后端业务错误仍返回稳定错误代码；前端优先按错误代码翻译，缺少翻译时显示服务端原始信息。
- 新生欢迎语在 `system_setting.setting_value` 中保存为 JSON 对象，至少包含 `zh-CN` 和 `en-US`。管理员分别编辑两种文本。
- 当前用户接口返回全部欢迎语语言版本，前端按当前语言即时选择，无需重新登录。

## 床位拆分规则

- 编辑器以床具单元而不是床位层级展示类型：`LOFT_BED_DESK` 表示上床下桌，`BUNK` 表示上下铺。
- 已有上下铺的上铺和下铺继续作为两个独立床位存储，共享同一个 `bed_frame`、坐标和朝向。
- 将空的上床下桌改为上下铺时，后端事务内执行：
  1. 校验房间当前容量小于八人；
  2. 新建 `BUNK_FRAME`；
  3. 原床位改为 `BUNK_UPPER` 并绑定床架；
  4. 新建 `BUNK_LOWER`，生成不重复床位编号和排序号；
  5. 复制原床位的 `batch_bed_scope`；
  6. 为上下铺写入同一布局；
  7. 按新物理床位数量同步房型和容量。
- 非空床位不得拆分。
- 本阶段不提供上下铺合并回单床位，避免删除已被历史范围或业务记录引用的床位。
- 房间人数为四、五、六时分别同步标准房型；七、八人同步为其他房型。

## 界面规则

- 布局编辑器床位圆角矩形在桌面端放大为当前尺寸的一点六倍，即约 `304×144` 像素；移动端按相同比例调整但限制在可视区域内。
- 编辑器对话框使用不透明浅色背景，遮罩使用深色半透明背景，确保底层页面文字不会透入对话框。
- 类型设置区按床具单元展示；上下铺只显示一个类型选择框，并标明包含两个可选床位。

## 验收

- 主页邀请弹窗、暂不确认、组队页邀请处理均正常。
- 队长可在存在未确认邀请时开始选寝，未确认邀请失效，选寝人数只包含已确认成员。
- 成员退队与进入个人选寝自动退队均有后端事务保护。
- 中文和英语切换后，应用外壳、组队、选寝、欢迎语和宿舍编辑器立即更新。
- 管理员可保存两种语言欢迎语，学生欢迎弹窗按当前语言显示。
- 空上床下桌拆分后新增一个床位、容量增加一人、房型同步；容量达到八人时拒绝继续拆分。
- OpenAPI 生成、Java 构建、TypeScript 检查、前端生产构建、MySQL/Redis 真实冒烟全部通过。
