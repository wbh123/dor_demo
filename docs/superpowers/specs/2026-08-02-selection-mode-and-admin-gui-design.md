# 批次选择模式与管理员图形化界面设计

## 1. 背景与目标

现有系统默认按“学生进入寝室后选择具体床位”运行。新增需求要求同时支持：

- 选择寝室模式；
- 选择床位模式；
- 选择床位模式作为可独立授权的细粒度功能；
- 同一寝室在同一时间只能属于一个活动批次；
- 选择寝室后由系统随机分配该寝室内的可用床位；
- 批次结束后，寝室可重新用于任意选择模式；
- 管理员端继续减少 JSON 输入和 JSON 原始展示；
- 平台功能授权卡片进一步缩小，提高同屏信息密度。

本设计保持单客户、单学校、单实例边界，不引入多租户字段或租户识别逻辑。

## 2. 术语与模式

批次选择模式固定为：

```text
ROOM：学生选择寝室，系统随机分配床位
BED：学生选择具体床位
```

数据库字段使用 `selection_mode`，接口字段使用 `selectionMode`。

模式含义：

| 模式 | 学生可见操作 | 最终床位产生方式 |
|---|---|---|
| `ROOM` | 选择寝室 | 事务内随机分配寝室中的可用床位 |
| `BED` | 查看床位布局、临时占用、确认床位 | 学生确认具体床位 |

批次发布后不得修改选择模式。批次复制保留来源批次的选择模式，但新副本仍为草稿。

## 3. 功能权限设计

### 3.1 基础能力

`P1_SELF_SELECTION` 继续表示学生自选能力，包含选择寝室模式。

### 3.2 细粒度床位选择权限

新增功能代码：

```text
P2_BED_SELECTION_MODE
```

功能属性：

```text
phase = PHASE2
scope = SHARED
granularity = OPERATION
action_type = START_NEW
risk_level = MEDIUM
enabled_in_program = 1
```

规则：

1. 创建或发布 `ROOM` 批次只要求 `P1_SELF_SELECTION`；
2. 创建或发布 `BED` 批次同时要求：
   - `P1_SELF_SELECTION`；
   - `P2_BED_SELECTION_MODE`；
3. 前端根据有效权限决定模式卡片是否可选；
4. 后端在创建和发布两个时间点均重新校验，不能只依赖前端；
5. 现有批次迁移为 `BED`，以保持当前语义；
6. 当前默认完整套餐加入 `P2_BED_SELECTION_MODE`，避免升级后现有功能突然关闭；
7. 已经启动并拥有权限快照的 `BED` 批次继续按快照完成；紧急停止仍优先拒绝。

## 4. 数据库设计

新增 Flyway 正向迁移 `V15__add_batch_selection_modes.sql`，不得修改 V1 至 V14。

### 4.1 selection_batch

新增：

```sql
selection_mode VARCHAR(16) NOT NULL DEFAULT 'BED'
```

约束：

```sql
CHECK (selection_mode IN ('ROOM','BED'))
```

所有历史批次设置为 `BED`。

### 4.2 活动房间锁

新增表：

```text
active_batch_room_lock
```

字段：

| 字段 | 含义 |
|---|---|
| `room_id` | 房间主键，同时作为唯一占用键 |
| `batch_id` | 当前占用该房间的批次 |
| `selection_mode` | 锁定时的模式快照 |
| `locked_at` | 加锁时间 |

约束：

- `room_id` 唯一；
- 同一批次同一房间只能出现一条；
- 外键指向 `room` 和 `selection_batch`；
- 只表示活动批次资源占用，不表示学生分配。

### 4.3 分配方式

`bed_assignment.assignment_method` 和 `assignment_history.assignment_method` 增加：

```text
ROOM_SELECT_RANDOM
TEAM_ROOM_SELECT_RANDOM
```

含义：

- `ROOM_SELECT_RANDOM`：个人选择寝室后随机床位；
- `TEAM_ROOM_SELECT_RANDOM`：队伍选择寝室后随机多张床位。

### 4.4 功能目录初始化

向 `feature_catalog` 增加 `P2_BED_SELECTION_MODE`，并加入默认完整套餐的当前修订。

## 5. 活动房间互斥

### 5.1 需要加锁的批次状态

以下状态视为活动状态：

```text
PUBLISHED
OPEN
PAUSED
```

选择在 `PUBLISHED` 时提前锁定房间，保证学生填写问卷和查看候选范围期间，房间不会被另一个批次抢占。

### 5.2 实际房间范围计算

发布前根据以下范围并集计算批次涉及的房间：

1. `batch_room_scope` 直接指定的房间；
2. `batch_building_scope` 指定楼栋下的启用房间；
3. `batch_bed_scope` 中床位所属的房间。

结果去重后写入 `active_batch_room_lock`。

### 5.3 加锁事务

批次从非活动状态进入活动状态时，在同一事务中：

1. 锁定批次记录；
2. 校验选择模式权限；
3. 计算房间范围；
4. 按房间编号稳定排序；
5. 插入活动房间锁；
6. 若任一房间已被其他活动批次占用，整体回滚；
7. 返回冲突批次和冲突房间的自然语言摘要；
8. 再更新批次状态。

错误代码：

```text
BATCH_ROOM_ACTIVE_CONFLICT
```

错误详情至少包含：

```json
{
  "conflictingBatchId": 12,
  "conflictingBatchName": "2026级第一轮选寝",
  "rooms": ["南一栋-301", "南一栋-302"]
}
```

### 5.4 释放房间锁

批次从活动状态进入以下状态时释放：

```text
CLOSED
ALLOCATING
FINISHED
CANCELLED
```

`CLOSED` 表示学生选择已经结束，因此房间可供后续批次使用。原批次已有床位分配仍然保留，后续批次是否允许使用这些床位由批次范围和床位可用性校验决定。

### 5.5 并发要求

必须覆盖：

- 两个批次同时发布同一房间；
- 一个批次按楼栋范围发布，另一个按房间范围发布；
- 一个批次按床位范围发布，另一个按房间范围发布；
- 一个批次结束释放锁，同时另一个批次发布；
- 发布失败不得留下部分锁。

## 6. 个人选择寝室流程

新增接口：

```http
POST /api/v1/student/batches/{batchId}/rooms/{roomId}/select
```

请求不包含床位编号，也不使用 Redis 临时占用令牌。

### 6.1 事务流程

在一个数据库事务中：

1. 锁定批次和学生资格；
2. 校验批次为 `ROOM` 模式；
3. 校验批次状态为 `OPEN`；
4. 校验学生尚未在该批次获得分配；
5. 校验房间属于该批次范围；
6. 校验房间性别和运行状态；
7. 查询该房间启用且未分配的床位并使用 `FOR UPDATE` 锁定；
8. 使用安全随机算法从候选床位中随机选择一个；
9. 写入 `bed_assignment`，方式为 `ROOM_SELECT_RANDOM`；
10. 写入 `assignment_history`；
11. 写业务审计；
12. 提交后发送房间状态更新事件；
13. 返回最终房间和床位信息。

当房间已经无可用床位时返回：

```text
ROOM_NO_AVAILABLE_BED
```

并发情况下只能有一个事务获得最后一张床位。

### 6.2 随机性

随机选择只在当前事务锁定后的可用床位集合中进行。为了便于审计，历史数据记录：

- 候选床位数量；
- 最终床位编号；
- 随机分配方式；
- 操作时间。

不需要向学生展示随机种子。

## 7. 队伍选择寝室流程

新增接口：

```http
POST /api/v1/student/batches/{batchId}/teams/{teamId}/rooms/{roomId}/select
```

仅队长可操作。

事务流程：

1. 锁定队伍和有效成员；
2. 校验队伍属于该批次且已锁定；
3. 校验批次为 `ROOM` 模式；
4. 校验有效成员均未分配；
5. 锁定目标房间的可用床位；
6. 可用床位数必须不少于有效成员数；
7. 随机抽取与成员数相同的床位；
8. 对成员稳定排序，对抽取床位随机排序后逐一分配；
9. 每人写入 `TEAM_ROOM_SELECT_RANDOM` 分配；
10. 任一写入失败整体回滚；
11. 队伍状态改为 `COMPLETED`；
12. 提交后发送房间更新事件。

错误代码：

```text
ROOM_CAPACITY_NOT_ENOUGH_FOR_TEAM
```

不允许把一个队伍拆分到多个寝室。

## 8. 选择床位模式保护

现有以下接口仅允许 `BED` 模式：

```text
查看床位布局
个人临时占用床位
释放个人占用
确认个人床位
队伍临时占用床位
释放队伍占用
确认队伍床位
三维床位选择
```

若批次为 `ROOM` 模式，返回：

```text
BATCH_SELECTION_MODE_MISMATCH
```

学生候选寝室列表在两种模式下均可访问，但返回 `selectionMode` 和自然语言说明。`ROOM` 模式下不返回可操作的床位列表。

## 9. 管理员批次界面

### 9.1 创建批次

使用两张可点击模式卡片：

- 选择寝室；
- 选择床位。

每张卡片展示：

- 图标；
- 简短说明；
- 学生操作过程；
- 最终分配方式；
- 当前是否可用。

当 `P2_BED_SELECTION_MODE` 未授权时：

- “选择床位”卡片置灰；
- 显示“当前服务未开放该模式”；
- 默认选择 `ROOM`；
- 不展示功能代码。

### 9.2 批次列表

每个批次显示模式徽章：

```text
选择寝室
选择床位
```

发布前提供“房间占用检查”按钮，图形化展示：

- 涉及房间数量；
- 可正常锁定数量；
- 冲突数量；
- 冲突房间和占用批次。

不使用 JSON 展示冲突结果。

### 9.3 发布后锁定

模式在 `DRAFT` 状态可修改；进入 `PUBLISHED` 后界面禁止修改并显示锁定提示。

## 10. 学生界面

### 10.1 ROOM 模式

候选寝室卡片显示：

- 楼栋、楼层、房间号；
- 房型；
- 剩余床位数；
- 匹配分数；
- 匹配标签和注意事项；
- “选择此寝室”主按钮。

点击后弹出确认框：

```text
确认选择该寝室后，系统会随机安排其中一张可用床位，分配结果将立即生效。
```

确认后直接显示最终分配结果，不进入床位详情页。

### 10.2 BED 模式

保持当前寝室详情、床位布局、临时占用和确认流程。

### 10.3 路由保护

若学生手工访问 ROOM 批次的床位详情页，前端跳回寝室列表并显示自然提示；后端仍执行最终保护。

## 11. 平台功能授权卡片缩小

`PlatformFeaturesView.vue` 调整为紧凑卡片：

- 桌面端默认三列；
- 取消固定最小高度；
- 内边距由 16 像素降低为 10 至 12 像素；
- 功能名称、主要状态和滑动开关放在首行；
- 功能代码默认不显示；
- 点击“详情”展开后显示功能代码、范围、风险、默认状态和最近覆盖时间；
- 标签压缩为最多两个主要标签，其余放入详情；
- 底部“恢复套餐默认”改为小型图标按钮；
- 批量编辑能力保持不变；
- 未来功能仍禁用。

小屏幕布局：

```text
宽屏：3列
中屏：2列
手机：1列
```

## 13. 开放接口契约

根开放接口契约增加或调整：

- `BatchRequest.selectionMode`；
- 批次响应中的 `selectionMode`；
- 房间占用预检接口；
- 个人选择寝室接口；
- 队伍选择寝室接口；
- 候选寝室响应中的模式说明；
- 结构化冲突响应；
- 新分配方式枚举。

控制器继续实现生成接口，不新增第二套手写接口体系。

## 14. 服务拆分

为避免继续扩大 `StudentService`，新增独立服务：

```text
BatchSelectionModeService
ActiveBatchRoomLockService
RoomSelectionService
TeamRoomSelectionService
```

职责：

- `BatchSelectionModeService`：模式读取、模式权限校验、状态保护；
- `ActiveBatchRoomLockService`：房间范围计算、预检、加锁、释放；
- `RoomSelectionService`：个人选择寝室并随机分床；
- `TeamRoomSelectionService`：队伍选择寝室并随机分配多床。

现有床位模式逻辑调用 `BatchSelectionModeService.requireBedMode(...)` 进行保护。

## 15. 审计与事件

新增审计操作：

```text
BATCH_SELECTION_MODE_SET
BATCH_ROOM_LOCK_ACQUIRE
BATCH_ROOM_LOCK_RELEASE
ROOM_SELECT_RANDOM_ASSIGN
TEAM_ROOM_SELECT_RANDOM_ASSIGN
```

房间选择成功后发送：

```text
ROOM_ASSIGNMENT_CHANGED
```

事件内容只包含必要的房间状态变化，不泄露学生个人信息。

## 16. 错误处理

8. BED 模式原有个人和队伍流程回归。

## 18. 迁移与兼容策略

- 历史批次统一设置为 `BED`；
- 默认完整套餐加入床位模式权限；
- 已发布或正在运行的历史批次保持原流程；
- 新建批次必须明确选择模式；
- 老客户端未提交 `selectionMode` 时，后端暂时回落为 `BED`，并记录兼容警告；
- 前端更新后始终显式提交模式；
- 后续版本可移除老客户端回落逻辑。

## 19. 非目标

本轮不实现：

- 同一批次内按房间混合 ROOM 和 BED；
- 学生先选寝室后再在寝室内二次选床；
- 跨寝室拆分队伍；
- 房间预占的 Redis 临时令牌；
- 多租户或多学校隔离；
- 对已完成分配的历史批次重新随机。

## 20. 验收标准

满足以下条件才可声明完成：

1. `main` 中存在 V15 且真实迁移通过；
2. 管理员可图形化选择 ROOM 或 BED；
3. BED 模式受细粒度权限控制；
4. 同一寝室不能同时进入两个活动批次；
5. ROOM 模式个人选择后原子随机分床；
6. ROOM 模式队伍可在同寝室完整分配；
7. 批次结束释放房间锁；
8. BED 模式现有流程不回退；
9. 权限卡片明显缩小并支持三列；
10. 管理员主要页面不再依赖原始 JSON 输入或展示；
11. Maven、前端构建、数据库迁移和真实接口冒烟均有实际退出码和结果。
