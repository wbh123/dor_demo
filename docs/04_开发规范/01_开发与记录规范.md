# 开发与记录规范

> 文档编号：DOC-DEV-STD-001  
> 创建日期：2026-08-01  
> 状态：初始规范

## 1. 开发基本流程

每一项功能按以下顺序推进：

```text
确认当前阶段与范围
→ 阅读根目录和相关目录 AGENTS.md
→ 阅读需求、设计和现有代码
→ 明确数据库、接口和前端影响
→ 编写或更新测试
→ 实现功能
→ 执行真实验证
→ 更新文档与 records
→ 提交并审查
```

不得在未理解现有约束时直接重写稳定模块。

## 2. 需求变更

重要需求变化必须同步更新：

- 项目级需求文档；
- 当前阶段计划；
- OpenAPI；
- 数据库迁移设计；
- 前端交互说明；
- 测试与验收设计；
- 开发记录。

只在聊天或提交信息中说明，不视为完成需求变更记录。

## 3. 后端开发

### 3.1 OpenAPI 优先

- 新增或变更外部接口时先修改 OpenAPI；
- 生成代码不能手工长期修改；
- 控制器实现生成接口；
- 接口使用稳定错误码；
- 生成代码与手写业务代码分离；
- 构建中检查契约和生成结果一致性。

### 3.2 分层

建议保持：

```text
Controller
→ Application Service
→ Domain/Business Service
→ Repository/Mapper/External Adapter
```

- Controller 不直接访问 Mapper、Redis 或导出组件；
- 业务规则集中在业务服务；
- 数据转换使用明确的转换器；
- 持久化实体不直接作为接口响应；
- 事务边界由应用服务或专用事务服务控制。

### 3.3 数据库

- 数据库结构使用版本化迁移；
- 已执行迁移不得修改，应新增迁移；
- 最终分配唯一性必须由数据库约束保证；
- 关键状态字段使用明确枚举或受控值；
- 删除学生、房间、批次和分配时优先考虑历史追溯；
- 索引根据查询和约束设计，不盲目添加；
- 普通构建不得连接业务数据库生成代码。

### 3.4 Redis

- 键名包含系统、业务、批次和资源范围；
- 所有临时键设置过期时间；
- 原子操作优先使用 `SET NX`、事务或 Lua；
- 删除和续期必须校验令牌；
- 缓存必须有失效和重建方式；
- Redis 故障不能导致数据库出现重复分配；
- 不把永久业务事实只保存在 Redis。

### 3.5 Java 包和目录

- 根包：`com.wust.dormitory`；
- 包声明与目录严格一致；
- 启动类位于根包目录，使 Spring 能扫描子包；
- Mapper 接口、映射文件和扫描配置一致；
- 新增目录前检查相关 `AGENTS.md`；
- 不保留 `com/com/...` 或无意义重复层级。

## 4. 前端开发

- 使用 TypeScript；
- 接口类型尽量由 OpenAPI 生成；
- 页面状态与服务端权威状态分开；
- 关键请求处理加载、成功、失败和重试；
- 防止重复点击造成重复提交；
- 路由离开和组件销毁时释放服务器发送事件连接；
- 重连后重新获取快照；
- 不在本地存储其他学生敏感资料；
- 选寝和倒计时使用服务端时间校正；
- 五人间布局以床位数据驱动，不写死为普通四人间。

## 5. 测试规范

### 5.1 后端

至少包括：

- 单元测试；
- Spring 集成测试；
- 数据库真实约束测试；
- Redis 原子操作与过期测试；
- OpenAPI 接口测试；
- 并发冲突测试；
- HTTP 主流程验收。

### 5.2 前端

至少包括：

- 类型检查；
- 组件和业务函数测试；
- 关键页面交互测试；
- 服务器发送事件状态处理测试；
- 生产构建；
- 必要的端到端流程测试。

### 5.3 算法

匹配和随机分配必须提供：

- 固定输入和预期输出；
- 权重边界；
- 空房间、满房间和单成员房间；
- 严重冲突项；
- 无候选；
- 相同分数；
- 随机种子复现；
- 性能规模测试；
- 公平性和异常案例说明。

### 5.4 验证声明

- 只报告实际执行过的命令；
- 记录真实通过、失败和跳过数量；
- 依赖或环境缺失时明确说明；
- 不使用旧提交的测试结果证明新提交；
- 不通过删除测试、放宽断言或捕获所有异常绕过失败。

## 6. 配置和敏感信息

- 根目录配置示例只保存占位值；
- 本地真实配置加入 Git 忽略；
- 密码、令牌、密钥、数据库备份和真实学生数据不得提交；
- 日志、截图、文档和拉取请求不得粘贴真实凭据；
- 学生样例数据使用虚构内容；
- 导出文件和本地持久化目录默认不提交。

## 7. Git 规范

### 7.1 分支

- 功能开发优先使用独立分支；
- 分支名称说明主题；
- 不在分支中混入无关修改；
- 合入前检查与主分支差异。

### 7.2 提交信息

推荐格式：

```text
<type>(<scope>): <中文摘要>
```

常用类型：

- `feat`：功能；
- `fix`：修复；
- `docs`：文档；
- `test`：测试；
- `refactor`：不改变行为的重构；
- `build`：构建和依赖；
- `ci`：持续集成；
- `chore`：其他维护。

示例：

```text
feat(selection): 实现床位临时占用
fix(backend): 修复启动类包目录
```

用户要求控制提交数量时，应通过规划、交互式暂存或压缩提交满足要求。

## 8. `records` 记录

建议结构：

```text
records/
├── PROJECT_LOG.md
├── PROMPT_INDEX.md
├── DAILY/
├── DECISIONS/
└── TESTS/
```

每次开发记录至少包含：

- 日期时间；
- 用户原始要求；
- 当前分支和提交；
- 阅读的关键文档；
- 自主决策；
- 修改文件；
- 数据库与接口变化；
- 测试命令和结果；
- 已知限制；
- 下一步。

## 9. 阶段验收与冻结

阶段完成时：

1. 汇总功能完成情况；
2. 执行当前提交的全套验证；
3. 记录失败和未完成项；
4. 更新 README 和阶段状态；
5. 形成实施与验收记录；
6. 形成冻结说明；
7. 明确后续阶段可复用和禁止回退的边界。

没有真实测试结果时，不得标记阶段已完成或已冻结。
