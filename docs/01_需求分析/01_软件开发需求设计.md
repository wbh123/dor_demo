# 软件开发需求设计

> 文档编号：DOC-REQ-DEV-001  
> 创建日期：2026-08-01  
> 适用对象：产品、前端、后端、测试和运维开发人员  
> 状态：第一版需求基线

## 1. 系统目标

系统需要完成从学生和宿舍资源导入、选寝批次配置、生活习惯填写、个人或组队选寝、临时占用、实时状态同步、最终确认，到未选学生随机分配、结果导出和异常调整的完整业务闭环。

当前采用单实例部署。学院管理员和宿舍管理员合并为统一管理角色。系统不使用大语言模型进行匹配或分配。

## 2. 术语

| 术语 | 含义 |
|---|---|
| 选寝批次 | 一组具有共同适用学生、宿舍范围、开放时间和规则的选寝活动 |
| 资格 | 学生是否允许参与某一批次，以及可选的楼栋、房型和床位范围 |
| 临时占用 | 学生提交最终选择前，由 Redis 保存的短时独占权 |
| 最终分配 | 经过数据库事务确认的学生与床位归属关系 |
| 随机选择 | 学生主动请求系统推荐一个或多个候选床位 |
| 随机分配 | 管理人员或系统对未选学生进行批量分配 |
| 组队 | 多名学生组成选寝单位，共同选择同一房间或相邻床位 |
| 匹配分 | 依据问卷特征和配置权重计算的相似度，仅用于辅助推荐 |

## 3. 角色与权限

### 3.1 学生

学生只能访问本人和当前批次允许公开的数据：

- 登录、退出和查看本人账户状态；
- 查看本人选寝资格、批次时间和规则；
- 修改允许编辑的个人资料；
- 填写和提交生活习惯问卷；
- 查看候选宿舍、房间、床位状态和公开室友标签；
- 创建、加入、退出、解散和锁定队伍；
- 申请临时占用、续期、释放和最终提交；
- 使用随机选择；
- 查看本人操作结果和最终分配。

学生不得：

- 查看他人完整问卷和隐私信息；
- 修改他人资料；
- 订阅无权访问的房间状态；
- 在批次未开放、已关闭或本人已完成选寝后继续占用床位；
- 绕过队伍状态单独改变已锁定队伍的选择。

### 3.2 宿舍管理人员

- 管理学生和组织信息；
- 管理校区、楼栋、楼层、房间、床架和床位；
- 创建、复制、修改、发布、暂停和关闭选寝批次；
- 配置资格、宿舍范围、时间、占用时长、问卷权重和随机规则；
- 查看批次进度、房间状态和异常事件；
- 执行统一随机分配和补充分配；
- 对分配结果进行有原因的人工调整；
- 导出学生分配结果和统计；
- 查询操作日志和分配历史。

## 4. 数据导入与基础资源

### 4.1 学生导入

系统应支持通过表格导入学生，至少包含：

- 学号；
- 姓名；
- 性别；
- 学院；
- 专业；
- 年级；
- 班级；
- 校区；
- 住宿资格状态；
- 可选扩展字段。

要求：

- 学号在学校范围内唯一；
- 导入前提供字段校验和错误预览；
- 支持新增、更新和仅校验模式；
- 错误行不得影响正确行的明确处理结果；
- 导入结果应记录批次、操作者和错误原因。

### 4.2 宿舍资源

层级模型：

```text
校区
→ 宿舍楼
→ 楼层
→ 房间
→ 床架（可选）
→ 床位
```

房间至少包含：房间编号、房型、容量、性别限制、状态和备注。

床位至少包含：床位编号、床位类型、位置序号、所属房间、所属床架、启用状态和排序号。

五人间固定支持：

- 三个上床下桌床位；
- 一个独立床架上铺；
- 同一床架下铺；
- 五个床位均有独立床位编号和占用状态；
- 上铺和下铺通过同一床架编号建立关联。

## 5. 选寝批次

### 5.1 批次状态

建议状态：

```text
DRAFT 草稿
→ PUBLISHED 已发布待开放
→ OPEN 进行中
→ PAUSED 已暂停
→ CLOSED 已关闭
→ ALLOCATING 随机分配中
→ FINISHED 已完成
→ CANCELLED 已取消
```

状态转换必须由后端校验，不允许任意跳转。

### 5.2 批次配置

至少包含：

- 批次名称和说明；
- 适用学生范围；
- 可选校区、楼栋、房间和床位范围；
- 开始时间和结束时间；
- 临时占用时长；
- 是否允许组队；
- 队伍最小和最大人数；
- 是否允许学生随机选择；
- 未选学生处理方式；
- 匹配算法版本和权重方案；
- 结果公示设置；
- 规则版本。

发布前必须检查：

- 时间合法；
- 学生范围非空；
- 宿舍容量可计算；
- 床位没有重复归属；
- 性别和校区规则不冲突；
- 当前批次不会与同一学生的其他开放批次冲突。

## 6. 生活习惯问卷

### 6.1 建议维度

- 起床时间；
- 入睡时间；
- 午休习惯；
- 睡眠敏感程度；
- 可接受噪声；
- 卫生与清洁频率；
- 室内整洁要求；
- 空调温度偏好；
- 通风偏好；
- 宿舍内学习频率；
- 游戏或语音频率；
- 社交活跃程度；
- 是否吸烟等学校允许采集的关键冲突项；
- 床位类型偏好。

具体问题必须由校方确认，避免采集与住宿分配无关的敏感信息。

### 6.2 数据规则

- 问卷版本化；
- 批次可以绑定指定问卷版本；
- 答案转换为标准化特征向量；
- 原始答案与计算特征分开保存；
- 学生可在批次规则允许时修改；
- 提交选寝后是否允许修改由批次配置决定；
- 公开给其他学生的信息应是概括标签，而非完整答案。

## 7. 个人自主选寝

### 7.1 查看房间

学生可按楼栋、楼层、房型、剩余床位、床位类型和匹配度筛选。

房间列表至少返回：

- 房间基础信息；
- 总床位数和剩余床位数；
- 各床位状态摘要；
- 当前已入住成员的非敏感标签；
- 本人与房间的匹配分和主要解释；
- 数据版本或更新时间。

### 7.2 临时占用

申请占用前校验：

- 学生已登录；
- 批次处于开放状态；
- 当前时间在有效窗口内；
- 学生具有资格且未完成选寝；
- 学生未被锁定在其他有效队伍选择中；
- 床位属于本批次允许范围；
- 床位未禁用、未最终占用；
- Redis 中不存在其他有效占用。

成功后返回：占用令牌、床位编号、过期时间、服务端时间和房间版本。

### 7.3 最终提交

提交必须携带占用令牌。后端在同一事务中：

1. 再次校验批次、学生、床位和令牌；
2. 锁定或条件更新必要数据库记录；
3. 写入最终分配；
4. 更新床位和学生选寝状态；
5. 写入业务事件和审计；
6. 提交事务；
7. 安全释放临时占用；
8. 发布房间状态变化事件。

数据库必须通过唯一约束阻止重复分配。

## 8. 组队选寝

### 8.1 队伍状态

```text
FORMING 组建中
→ LOCKED 已锁定
→ SELECTING 选寝中
→ COMPLETED 已完成
→ DISSOLVED 已解散
```

### 8.2 核心规则

- 每名学生在同一批次只能加入一个有效队伍；
- 邀请需要被邀请人确认；
- 队伍人数不能超过批次上限；
- 锁定后普通成员不能随意退出；
- 队长选择的房间必须有足够可用床位；
- 可以由系统为成员分配房内具体床位，或由队伍成员按规则分别确认；
- 任一成员无资格、已分配或状态异常时不得提交；
- 组队最终提交应尽量使用一次业务事务完成；
- 部分成功必须被禁止或有明确补偿方案。

第一阶段实现基础完整队伍选择，复杂的跨房间、候补和队伍合并放入后续阶段。

## 9. 随机选择与统一随机分配

### 9.1 学生随机选择

学生点击随机选择后：

1. 应用硬约束过滤；
2. 排除已满、禁用和不可访问房间；
3. 计算本人对候选房间的匹配分；
4. 在高分候选中按明确策略抽取；
5. 返回候选及选择理由；
6. 学生确认后再申请临时占用，不得直接形成最终分配。

可以支持“换一个”操作，但需要限制频率，防止无意义高频计算。

### 9.2 统一随机分配

对未完成学生分配时必须：

- 固化学生集合和可用床位快照；
- 记录算法版本、规则版本、执行人、执行时间和执行编号；
- 先满足硬约束；
- 可按队伍、特殊需求、匹配度和公平规则分组处理；
- 对无法分配学生输出明确原因；
- 支持预演，不写入正式结果；
- 正式执行应幂等，重复请求不得重复分配；
- 生成结果摘要和异常清单。

## 10. 实时推送

### 10.1 连接范围

学生进入房间详情或选寝页面时，按批次和房间建立服务器发送事件连接。

建议端点形式：

```text
GET /api/v1/batches/{batchId}/rooms/{roomId}/events
```

### 10.2 事件类型

- `ROOM_SNAPSHOT`：初始快照；
- `BED_HELD`：床位被临时占用；
- `BED_RELEASED`：占用释放或过期；
- `BED_ASSIGNED`：床位最终分配；
- `ROOM_UPDATED`：房间配置变化；
- `BATCH_STATUS_CHANGED`：批次状态变化；
- `HEARTBEAT`：心跳；
- `RESYNC_REQUIRED`：客户端需要重新获取快照。

事件不得包含敏感个人信息。每个事件应有递增版本或可比较版本，以帮助客户端识别乱序和遗漏。

### 10.3 生命周期

- 页面打开建立连接；
- 页面离开主动关闭；
- 服务端定时心跳；
- 连接异常时浏览器按退避策略重连；
- 重连后依据最后事件编号尝试恢复，无法恢复则重新获取快照；
- 服务端定期清理完成、超时或异常连接；
- 推送失败不回滚已提交的数据库事务。

## 11. 匹配推荐

### 11.1 硬约束

硬约束不参与打分，必须先过滤：

- 批次和住宿资格；
- 性别和校区；
- 房型和容量；
- 管理人员配置的楼栋或专业范围；
- 特殊住宿条件；
- 床位启用状态。

### 11.2 软偏好

将问卷转换为标准化向量。可采用加权距离：

```text
学生距离 = Σ(特征权重 × 特征差异)
学生相似度 = 1 - 归一化距离
```

离散冲突项可以使用预定义差异矩阵，而不是简单数字相减。

房间评分建议综合：

- 与已入住成员的平均相似度；
- 与最不匹配成员的相似度；
- 关键冲突项惩罚；
- 房间剩余容量；
- 床位类型偏好；
- 批次策略加分或减分。

### 11.3 秒级检索

- 问卷提交时预计算学生特征；
- 房间成员变化时增量更新房间特征中心和关键标签；
- 先按硬约束和特征桶缩小候选；
- 对候选集合计算精确分数并取前若干名；
- 热门结果可短期缓存，但成员变化后必须失效；
- 记录算法版本和权重版本；
- 通过固定规模性能测试验证响应时间。

## 12. 管理调整与审计

所有人工调整必须：

- 校验目标床位有效且无冲突；
- 填写调整原因；
- 保存调整前结果；
- 保存调整后结果；
- 记录操作者、时间、请求编号和相关批次；
- 向受影响学生展示最终状态；
- 必要时触发房间推送。

不允许直接修改数据库绕过业务服务。

## 13. 非功能需求

### 13.1 一致性

- 数据库是最终事实来源；
- Redis 数据可过期和重建；
- 关键唯一约束必须落在数据库；
- 写操作需要幂等设计；
- 事务完成后再发布状态事件。

### 13.2 性能

第一版建议验收目标：

- 普通查询在正常测试数据规模下多数不超过 1 秒；
- 房间推荐在候选索引有效时不超过 2 秒；
- 临时占用结果应快速返回；
- 房间状态变化在正常网络下尽快推送；
- 并发指标在第一阶段详细计划中根据学校学生规模确定。

以上是设计目标，不应在未压测前声称已经达到。

### 13.3 安全

- 密码安全存储；
- 登录态过期和退出；
- 后端角色和对象范围校验；
- 表格导入防止公式注入和异常文件；
- 接口限流或频率控制覆盖随机选择、占用和登录；
- 日志不记录密码、令牌和完整敏感数据；
- 导出文件设置权限和有效期。

### 13.4 可维护性

- OpenAPI 为接口事实来源；
- 数据库结构通过版本化迁移维护；
- 业务状态使用明确枚举；
- 算法权重和规则版本化；
- 核心流程有自动化测试和 HTTP 验收；
- 每次开发同步文档和记录。

## 14. 第一阶段验收主流程

```text
管理人员导入学生和宿舍
→ 创建并发布批次
→ 学生登录和提交问卷
→ 两名学生同时申请同一床位
→ 只有一名获得占用
→ 获得占用者提交成功
→ 另一名看到实时状态变化并选择其他床位
→ 组队学生完成同房选择
→ 未选学生执行随机分配预演和正式分配
→ 管理人员导出结果并查询审计
```

该流程以及失败分支应形成自动化测试和可重复的 HTTP 验收脚本。
