# 开发阶段文档总索引

> 文档编号：DOC-PHASE-INDEX-001  
> 创建日期：2026-08-01  
> 状态：当前权威阶段规划

## 1. 阶段结构

```text
准备阶段
→ 第一阶段：核心选寝闭环
→ 第二阶段：完善、质量与运营能力
→ 第三阶段：可选增强能力
```

阶段按业务依赖推进。每个阶段完成后需要形成实施记录、测试结果和冻结说明，后续阶段原则上不重写已冻结的核心规则。

## 2. 当前阶段状态

| 阶段 | 状态 | 目标 |
|---|---|---|
| 准备阶段 | 进行中 | 检查工程、修复初始化问题、建立文档、环境和测试入口 |
| 第一阶段 | 待开发 | 形成可用的学生选寝和管理闭环 |
| 第二阶段 | 待开发 | 完善匹配、交互、异常处理、统计、安全和自动化质量 |
| 第三阶段 | 待评估 | 根据实际需求实现换寝、通知、候补和分析等可选功能 |

## 3. 准备阶段

### 3.1 目标

- 检查前后端工程结构；
- 修正 Java 包声明与目录不一致；
- 清理模板残留和示例命名；
- 建立项目 README、AGENTS、需求、设计和开发规范；
- 确认父级物料清单依赖和本地构建方式；
- 规划数据库迁移、OpenAPI 和测试目录；
- 建立根目录配置示例和敏感配置忽略规则；
- 记录当前工程已知限制。

### 3.2 完成标准

- Java 源码目录与包声明一致；
- 启动类位置与 Maven 配置一致；
- MyBatis 映射目录与运行配置一致；
- 文档入口可用且链接有效；
- 后端和前端构建命令明确；
- 当前未通过的构建或运行问题有真实记录；
- 第一阶段详细计划具备编写条件。

## 4. 第一阶段：核心选寝闭环

### 4.1 范围

#### 工程与基础

- 统一配置入口；
- 数据库迁移；
- 统一响应、错误码和请求编号；
- 登录认证和学生、管理人员角色；
- OpenAPI 生成和接口一致性检查；
- 基础持续集成。

#### 基础资源

- 学生和组织导入、查询和维护；
- 校区、楼栋、楼层、房间、床架和床位；
- 普通房型和特殊五人间；
- 房间和床位启用、禁用。

#### 批次与资格

- 批次状态；
- 适用学生和宿舍范围；
- 开放时间；
- 临时占用时长；
- 组队和随机选择开关；
- 资格查询和发布前校验。

#### 问卷与基础匹配

- 问卷版本；
- 学生答案；
- 标准化特征；
- 可配置权重；
- 学生与房间基础匹配分；
- 简单解释标签。

#### 选寝

- 房间和床位查询；
- Redis 个人临时占用；
- 占用倒计时、释放和过期；
- 数据库最终提交；
- 基础组队、队伍锁定和整体选寝；
- 学生随机选择；
- 未选学生统一随机分配预演和正式执行；
- 本人结果查询。

#### 实时与管理

- 房间级服务器发送事件；
- 心跳、重连和连接清理；
- 批次进度；
- 未选和异常列表；
- 人工调整；
- 结果导出；
- 操作审计。

### 4.2 第一阶段禁止扩张

- 不拆分微服务；
- 不引入消息队列和注册中心；
- 不实现多实例推送；
- 不接入大语言模型；
- 不实现完整换寝审批；
- 不追求复杂运筹最优解而阻塞核心交付；
- 不提前实现与验收无关的物联网或支付功能。

### 4.3 验收门禁

至少完成：

- 后端单元和集成测试；
- Redis 原子占用并发测试；
- 数据库唯一约束冲突测试；
- 组队整体成功和整体失败测试；
- 服务器发送事件连接与重连测试；
- 匹配算法固定样例和性能测试；
- 前端类型检查、测试和生产构建；
- 主流程 HTTP 验收；
- 数据导入、随机分配和导出验收；
- 第一阶段实施记录和冻结说明。

## 5. 第二阶段：完善与质量提升

### 5.1 功能完善

- 更丰富的筛选、排序和房间推荐；
- 关键冲突解释和权重管理界面；
- 房内床位分配建议；
- 复杂队伍异常处理；
- 批次复制和规则模板；
- 分配调整冲突预览；
- 更完整的进度、容量和异常统计；
- 更友好的床位布局和移动端页面。

### 5.2 工程质量

- 权限对象范围硬化；
- 接口频率限制；
- 表格导入安全；
- 更完整的审计和导出安全；
- 数据库索引和慢查询优化；
- Redis 故障和重启恢复策略；
- 大规模并发压测；
- 可观测性、日志和备份说明；
- 连续演示数据和自动验收脚本。

### 5.3 算法完善

- 特征桶和候选索引；
- 房间聚合特征增量更新；
- 平均匹配与最差成员惩罚；
- 学生随机选择的带权抽样；
- 统一随机分配的贪心和局部交换优化；
- 公平性和极端案例评估；
- 算法版本、参数和随机种子追溯。

## 6. 第三阶段：可选增强能力

只有在第一、二阶段稳定后，根据学校真实需求选择：

- 换寝和调寝申请；
- 候补、释放床位自动补位；
- 邮件、短信或学校统一消息平台通知；
- 学院和宿舍部门权限细分；
- 特殊住宿需求审批协作；
- 历史住宿和资源利用分析；
- 宿舍容量预测和规划辅助；
- 移动应用或小程序；
- 生产部署、监控、备份和灾难恢复增强。

第三阶段功能需要单独确认需求、隐私边界和验收标准，不能默认为必须交付。

## 7. 阶段冻结规则

阶段冻结后：

- 已发布 OpenAPI 不做无兼容说明的破坏性修改；
- 已执行数据库迁移不得直接修改；
- 最终分配唯一约束不得弱化；
- Redis 临时占用与数据库最终事实边界不得颠倒；
- 前端不得自行计算正式分配结果；
- 匹配算法版本变更必须可追溯；
- 发现阻断缺陷可以修复，但需记录原因、影响和验证结果。
