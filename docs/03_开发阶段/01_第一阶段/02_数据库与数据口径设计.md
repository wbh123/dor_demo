# 第一阶段数据库与数据口径设计

> 文档编号：DOC-PHASE1-DB-001  
> 状态：第一阶段开发基线  
> 日期：2026-08-01  
> 数据库：MySQL 8.4  
> 迁移工具：Flyway  
> 当前迁移版本：V3

## 1. 数据库管理原则

开发期间，`backend-java/server/src/main/resources/db/migration/` 中的Flyway版本迁移是数据库结构的唯一事实来源。

固定规则：

- 已经执行的版本迁移不得修改；
- 表结构变化必须新增版本迁移；
- 正式启动默认只加载 `classpath:db/migration`；
- 合成测试数据放在 `src/test/resources/db/dev-migration`；
- 第一阶段全部功能验收后，运行 `python scripts/db/build_frozen_baseline.py`；
- 固化SQL是部署快照，不能反向代替开发期间的Flyway迁移；
- Redis只保存临时占用和可重建缓存，最终分配事实保存在MySQL。

## 2. 学生数据最小化

### 2.1 业务要求

学生业务信息只需要：

```text
学号
姓名
性别
专业编号
```

数据库使用技术主键和专业外键实现规范化，最终学生表字段为：

```text
id
student_number
student_name
gender
major_id
created_at
updated_at
```

其中：

- `student_number`为12位数字且全局唯一；
- `gender`只允许`M`或`F`；
- `major_id`关联`major`；
- 对外接口返回专业编号时，通过专业外键查询`major.major_code`。

### 2.2 删除的冗余字段

V3从学生表删除：

```text
user_id
organization_id
campus_id
grade_year
major_name
class_name
housing_eligibility
profile_status
data_source
version
```

删除原因：

- 用户账号属于认证域，关系改为 `app_user.student_id`；
- 当前需求不需要学院、班级和年级；
- 专业名称只保存在专业表，避免每名学生重复保存；
- 学生是否可参加选寝属于批次规则，保存在 `batch_student_eligibility`；
- 校区和可选宿舍由批次范围决定，不写入学生档案；
- 数据来源应由导入任务和审计记录追踪，而不是学生表永久字段。

### 2.3 专业表

`major`字段：

| 字段 | 说明 |
|---|---|
| `id` | 专业主键 |
| `major_code` | 学校专业编号，全局唯一 |
| `major_name` | 专业名称，全局唯一 |
| `enabled` | 是否启用 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

学生表只保存 `major_id`。专业编号或名称变化时只需修改一条专业记录。

### 2.4 账号关联

`app_user.student_id`用于学生账号关联：

- 学生账号保存对应学生主键；
- 管理员账号的`student_id`为空；
- `uk_app_user_student`保证一个学生最多绑定一个账号；
- 学生档案不保存登录名、密码或账户状态。

## 3. 宿舍房型与性别

当前测试配置：

- 男生为五人间，每间三个上床下桌和一组上下铺；
- 女生为四人间，每间四个上床下桌。

该组合只是当前需求，不是永久数据库限制。数据库将以下信息分开建模：

```text
room.room_type
room.capacity
room.gender_restriction
bed.bed_type
bed_frame
```

后续可以出现男女各自的四人间、五人间混合，但每个房间必须固定为`M`或`F`，不得男女混住。

管理员通过：

```text
batch_building_scope
batch_room_scope
batch_bed_scope
```

分别设置当前批次允许选择的楼栋、房间和床位。

## 4. 数据域

### 4.1 用户与学生

| 表 | 作用 |
|---|---|
| `major` | 专业编号与名称 |
| `student` | 最小化学生档案 |
| `app_user` | 学生和管理员账号 |
| `import_job` | 学生、专业或宿舍导入任务 |
| `import_error` | 导入错误行及原因 |

V3删除了`organization`。当前系统不维护班级层级，继续使用通用组织树会产生无用结构和重复数据。

### 4.2 宿舍资源

```text
campus
→ dormitory_building
→ dormitory_floor
→ room
→ bed_frame（可选）
→ bed
```

房间和床位均作为独立资源保存，不能只用房间剩余人数代替具体床位。

### 4.3 批次与资格

| 表 | 作用 |
|---|---|
| `selection_batch` | 选寝时间、状态和规则 |
| `batch_student_eligibility` | 学生在当前批次中的资格 |
| `batch_building_scope` | 可选楼栋 |
| `batch_room_scope` | 可选房间 |
| `batch_bed_scope` | 可选床位 |

住宿资格按批次维护，而不是学生全局属性。这样同一学生可以在一个批次有资格、另一个批次无资格，并保留明确原因。

### 4.4 问卷、组队与分配

问卷原始答案与标准化特征分开保存；组队状态和邀请单独保存；最终床位归属由：

```text
UNIQUE(batch_id, student_id)
UNIQUE(batch_id, bed_id)
```

阻止重复分配。

## 6. Flyway迁移

```text
backend-java/server/src/main/resources/db/migration/
├── V1__create_phase1_schema.sql
├── V2__enforce_fixed_room_gender.sql
└── V3__normalize_major_and_minimize_student.sql
```

V3升级顺序：

1. 创建专业表；
2. 将旧学生专业名称归并为专业记录；
3. 增加并填充学生专业外键；
4. 将学生账号关系迁移到`app_user.student_id`；
5. 删除旧外键、索引和冗余字段；
6. 删除不再使用的`organization`。

旧数据库只有专业名称，没有专业编号。V3会生成稳定的`LEGACY-...`临时专业编号，管理员导入学校正式专业目录后可以替换为真实编号。

开发测试数据只有显式配置以下位置时才执行：

```properties
WUST_DORMITORY_FLYWAY_LOCATIONS=classpath:db/migration,filesystem:backend-java/server/src/test/resources/db/dev-migration
```

## 7. 固化流程

开发过程中：

```text
修改设计
→ 先补测试
→ 新增Flyway迁移
→ 验证空库迁移
→ 验证已有数据库升级
→ 更新数据字典与阶段文档
```

第一阶段全部功能完成并验收后：

```bash
python scripts/db/build_frozen_baseline.py
```

输出 `backend-java/docs/sql/schema.sql`。固化文件不包含开发测试数据，原Flyway迁移继续保留用于历史追踪和增量升级。
