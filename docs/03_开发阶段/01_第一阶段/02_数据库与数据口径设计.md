# 第一阶段数据库与数据口径设计

> 文档编号：DOC-PHASE1-DB-001  
> 状态：第一阶段开发基线  
> 日期：2026-08-01  
> 数据库：MySQL 8.4  
> 迁移工具：Flyway

## 1. 数据库管理原则

第一阶段开发期间，`backend-java/server/src/main/resources/db/migration/` 中的 Flyway 版本迁移是数据库结构的唯一事实来源。

固定规则：

- 已经在任何共享环境执行过的版本迁移不得修改；
- 表结构变化必须新增 `V<版本>__<说明>.sql`；
- 正式启动默认只加载 `classpath:db/migration`；
- 合成测试数据放在 `src/test/resources/db/dev-migration`，不会随正式应用默认执行；
- 第一阶段全部功能开发并验收完成后，运行 `python scripts/db/build_frozen_baseline.py`；
- 固化脚本将已冻结迁移整理为 `backend-java/docs/sql/schema.sql`；
- 固化 SQL 是部署和审阅快照，开发期间不能反向替代 Flyway；
- Redis 只保存临时占用和可重建缓存，不保存最终床位归属。

## 2. 标识符和公共字段

- 业务表使用 `BIGINT` 自增主键；
- 对外接口不得依赖主键连续性；
- 学号使用 `CHAR(12)`，数据库约束为12位数字；
- 当前合成学号统一以 `2026` 开头；
- 时间字段使用 `DATETIME(3)`；
- 应用层统一按学校业务时区解释时间；
- 可修改核心表使用 `version` 作为乐观锁版本；
- 创建和更新时间统一使用 `created_at`、`updated_at`；
- 已被批次、分配或审计引用的业务事实不物理删除。

## 3. 房型、性别与批次范围规则

### 3.1 当前业务配置

当前测试和首版交付按以下配置准备：

- 男生宿舍为五人间；
- 男生五人间包含三个上床下桌和一组上下铺；
- 女生宿舍为四人间；
- 女生四人间包含四个上床下桌。

该配置只是当前学校需求，不作为数据库永久限制。

### 3.2 后续可调整能力

数据库将房型、容量、床位布局和宿舍性别分别建模，因此后续可以出现：

- 男生四人间和男生五人间并存；
- 女生四人间和女生五人间并存；
- 同一宿舍楼内不同房间采用不同房型；
- 管理员按选寝批次选择部分楼栋、部分房间或部分床位开放。

系统禁止男女混住。每个 `room` 必须具有明确的：

```text
gender_restriction = M 或 F
```

不得使用 `ANY` 表示可混住。

宿舍楼 `dormitory_building.gender_restriction` 可以保留 `ANY`，用于未来同一楼栋内按房间分别设置男寝和女寝；但房间自身仍必须固定为男寝或女寝。

### 3.3 房型与床位布局一致性

`room.room_type`、`room.capacity` 和实际有效床位数量必须一致。

第一阶段至少支持：

```text
FOUR_PERSON
FIVE_PERSON
SIX_PERSON
OTHER
```

发布批次前，业务服务必须校验：

- 房间性别为 `M` 或 `F`；
- 房间容量等于有效床位数量；
- 四人间、五人间的床位结构符合管理员配置；
- 双层床上铺和下铺共享同一床架；
- 禁用或维护中的房间、床位不能进入可选范围；
- 学生性别必须与房间性别一致。

### 3.4 管理员配置可选宿舍

批次通过以下表逐层配置可选范围：

```text
batch_building_scope
batch_room_scope
batch_bed_scope
```

管理员可以：

- 按楼栋整体开放；
- 在楼栋内仅开放指定房间；
- 在房间内排除维护、预留或禁用床位；
- 分别为不同批次设置男生和女生可选宿舍；
- 在后续房型混合时精确控制哪些四人间、五人间可选。

候选床位必须同时满足批次范围、学生性别、住宿资格、房间状态和床位状态。

## 4. 数据域

### 4.1 用户、学生和组织

| 表 | 作用 |
|---|---|
| `organization` | 学校、学院、专业和班级层级 |
| `app_user` | 学生和管理员账户 |
| `student` | 学生业务档案 |
| `import_job` | 学生或宿舍导入任务 |
| `import_error` | 导入错误行及原因 |

关键约束：

- `student.student_number` 全局唯一；
- 一个学生最多关联一个系统用户；
- 学生性别仅允许 `M` 或 `F`；
- 住宿资格和资料状态使用明确枚举；
- 合成数据使用 `data_source=SYNTHETIC_PHASE1` 标记。

### 4.2 宿舍资源

```text
campus
→ dormitory_building
→ dormitory_floor
→ room
→ bed_frame（可选）
→ bed
```

| 表 | 作用 |
|---|---|
| `campus` | 校区 |
| `dormitory_building` | 宿舍楼及楼栋层面的性别建议 |
| `dormitory_floor` | 楼层 |
| `room` | 房型、容量、固定性别、运行状态和实时版本 |
| `bed_frame` | 上下铺共享床架 |
| `bed` | 独立可分配床位 |

男生五人间当前示例：

```text
A、B、C：LOFT_BED_DESK
D-U：BUNK_UPPER
D-L：BUNK_LOWER
D-U 与 D-L 共享 bed_frame_id
```

女生四人间当前示例：

```text
A、B、C、D：LOFT_BED_DESK
```

五个或四个床位都作为独立资源保存，不能只使用房间剩余人数代替床位。

### 4.3 批次与资格

| 表 | 作用 |
|---|---|
| `selection_batch` | 选寝时间、状态和规则 |
| `batch_student_eligibility` | 学生参与资格 |
| `batch_building_scope` | 可选楼栋范围 |
| `batch_room_scope` | 可选房间范围 |
| `batch_bed_scope` | 可选床位范围 |

范围规则采用逐层收窄：

1. 批次至少配置一种宿舍范围；
2. 配置房间时，房间必须属于允许楼栋；
3. 配置床位时，床位必须属于允许房间；
4. 学生资格、性别、校区和宿舍范围全部通过后才能进入候选集；
5. 批次状态转换由应用层状态机控制。

### 4.4 问卷与匹配

| 表 | 作用 |
|---|---|
| `questionnaire_version` | 问卷版本 |
| `questionnaire_question` | 问卷题目 |
| `questionnaire_option` | 题目选项 |
| `questionnaire_answer` | 原始答案 |
| `student_feature` | 标准化特征和公开解释标签 |
| `matching_weight_scheme` | 匹配权重和冲突规则 |

原始答案与计算特征分开保存。算法升级可以重算特征，但不能覆盖原始答案。

### 4.5 组队

| 表 | 作用 |
|---|---|
| `selection_team` | 队伍和状态 |
| `selection_team_member` | 队伍成员 |
| `team_invitation` | 邀请和响应 |

`selection_team_member.active_marker` 是生成列。唯一索引：

```text
(batch_id, student_id, active_marker)
```

确保同一学生在同一批次最多属于一个有效队伍，同时允许保留退出和拒绝历史。

组队成员必须性别一致，且目标房间性别必须与全部成员一致。

### 4.6 最终分配

| 表 | 作用 |
|---|---|
| `bed_assignment` | 当前有效床位归属 |
| `assignment_history` | 分配、调整、取消和恢复历史 |

数据库最后防线：

```text
UNIQUE(batch_id, student_id)
UNIQUE(batch_id, bed_id)
```

因此同一批次中：

- 一个学生最多有一个当前有效床位；
- 一个床位最多分配给一个学生；
- Redis临时占用成功不能绕过数据库约束；
- 最终提交前必须再次校验学生和房间性别一致。

### 4.7 随机分配与审计

| 表 | 作用 |
|---|---|
| `allocation_run` | 预演或正式随机分配执行 |
| `allocation_run_result` | 每名学生的执行结果 |
| `audit_log` | 关键操作审计 |

正式随机分配必须保存执行编号、幂等键、算法版本、规则版本、随机种子及学生和床位快照。

## 6. Flyway迁移文件

```text
backend-java/server/src/main/resources/db/migration/
├── V1__create_phase1_schema.sql
└── V2__enforce_fixed_room_gender.sql

backend-java/server/src/test/resources/db/dev-migration/
└── R__development_test_data.sql
```

正式结构默认执行。开发数据只有在显式配置以下位置时才执行：

```properties
WUST_DORMITORY_FLYWAY_LOCATIONS=classpath:db/migration,filesystem:backend-java/server/src/test/resources/db/dev-migration
```

该配置只能用于专用本地开发数据库。

## 7. 固化流程

开发过程中：

```text
修改设计
→ 新增Flyway版本迁移
→ 执行空库迁移测试
→ 执行已有数据库升级测试
→ 更新数据库文档
```

第一阶段全部功能完成并验收后：

```bash
python scripts/db/build_frozen_baseline.py
```

输出：

```text
backend-java/docs/sql/schema.sql
```

固化文件只包含正式版本迁移，不包含开发测试数据。原Flyway迁移继续保留，用于历史追踪和增量升级。
