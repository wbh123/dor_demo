# 第一阶段测试数据使用说明

## 1. 数据内容

当前合成数据包括：

- 5个测试专业；
- 520名学生，男女各260名；
- 8栋宿舍楼，男女各4栋；
- 32个楼层；
- 64个男生五人间；
- 80个女生四人间；
- 144个房间；
- 640个独立床位，男女各320个；
- 一个已发布问卷版本；
- 一个默认匹配权重方案；
- 一个草稿测试批次；
- 520条批次资格；
- 520条标准化生活习惯特征。

测试专业：

```text
M001  测试专业1
M002  测试专业2
M003  测试专业3
M004  测试专业4
M005  测试专业5
```

520名学生按固定规则均匀关联到5个专业。学生表只保存学号、姓名、性别和专业外键，不保存班级、年级、学院、校区或专业名称快照。

## 2. 学号规则

全部学号为12位数字，以2026开头：

```text
202600000001
...
202600000520
```

学号在测试数据内唯一，数据库也建立唯一约束。

学生姓名采用“测试男生001”“测试女生001”等合成名称，不包含真实个人信息。

## 3. 宿舍规则

男生五人间当前布局：

```text
3个上床下桌
+ 1组上下铺
= 5个床位
```

女生四人间当前布局：

```text
4个上床下桌
= 4个床位
```

这只是当前测试配置。正式数据模型允许后续按房间配置四人间、五人间等不同房型，但每个房间必须固定为男寝或女寝。

## 4. 重新生成

```bash
python scripts/db/generate_development_data.py
```

生成文件：

```text
backend-java/server/src/test/resources/db/dev-migration/R__development_test_data.sql
```

生成器采用固定规则，相同版本代码每次生成的内容完全一致。

## 5. 自动化验证

```bash
python -m unittest scripts/db/test_database_baseline.py -v
```

测试检查：

- 520个学号均为12位数字且以2026开头；
- 学号不重复；
- 男女学生各260名；
- 学生专业外键覆盖5个专业；
- V3创建专业表并删除学生冗余字段；
- 测试数据不再写入组织和班级信息；
- 账号关系位于`app_user.student_id`；
- 男生五人间64个、女生四人间80个；
- 男女床位各320个；
- 房间性别固定；
- 数据结构支持未来四人间、五人间混合；
- Flyway固化工具包含V3且排除开发数据；
- 已提交测试数据与生成器输出一致。

## 6. 加载测试数据

根目录`.env`默认只执行正式结构迁移：

```properties
WUST_DORMITORY_FLYWAY_LOCATIONS=classpath:db/migration
```

在专用本地开发数据库中，可临时改为：

```properties
WUST_DORMITORY_FLYWAY_LOCATIONS=classpath:db/migration,filesystem:backend-java/server/src/test/resources/db/dev-migration
```

Flyway会先执行V1、V2、V3，再执行开发数据重复迁移。

开发数据使用固定测试主键，并会清理对应合成数据后重新生成，因此：

- 只允许在专用本地开发数据库或自动化测试数据库使用；
- 不得在含真实业务数据的数据库中启用；
- 生产环境不得加入`db/dev-migration`。

## 7. 测试账号

管理员账号：

```text
用户名：admin
密码：Dormitory@2026
```

密码使用`{noop}`形式，仅用于认证模块完成前的本地准备。生产环境不得保留该账号或密码。

每名学生对应一个`PENDING`状态账户，账户通过`app_user.student_id`关联学生，没有初始密码。后续认证开发阶段再确定激活流程。

## 8. 本地数据库升级提醒

已经执行过V1、V2的数据库启动后会自动执行V3。V3会：

1. 将原专业名称归并到专业表；
2. 为旧数据生成`LEGACY-...`临时专业编号；
3. 迁移账号关联；
4. 删除学生冗余字段和组织表。

若本地数据库只包含合成数据，也可以删除`data/mysql/`后重新从空库启动，以直接获得最新结构和测试数据。
