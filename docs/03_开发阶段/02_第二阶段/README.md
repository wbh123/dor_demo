## 3. 已完成子项目

### 3.1 逐房间床位布局配置

Flyway V5新增`room_bed_layout`。管理员可逐房间拖拽床位、调整坐标和朝向，上下铺作为同一床架整体移动；学生Three.js场景优先读取数据库布局，没有自定义记录时使用默认纵向布局。

固定规则：

- 不回写第一阶段`bed`表；
- 坐标和朝向受后端与数据库校验；
- 上下铺上下层共享平面位置和朝向；
- 保存必须提交完整床位集合、填写原因并校验`room.version`；
- 房间版本不在页面展示；
- 移动端提供数值输入，不仅依赖拖拽。

### 3.2 匹配运营与推荐解释

Flyway V6为匹配权重方案增加不可变修订。管理员可创建方案、创建新修订和切换启用状态；批次始终引用精确方案修订，因此后续修改不会改变历史批次结果。

固定规则：

- 权重与冲突规则使用中文运营表单维护；
- 修改必须填写原因并写审计；
- 学生候选房间按批次引用的修订确定性排序；
- 学生端分开展示推荐理由和注意事项；
- 不公开其他学生完整个人偏好；
- 算法提供固定输入输出和真实接口验收。

### 3.3 学生体验、个人偏好与床位维护

Flyway V7新增首次欢迎状态和系统设置，Flyway V8扩展高影响个人偏好。学生首页展示完整偏好、画像摘要和筛选入口；管理员可以配置欢迎语并维护空闲床位类型。

固定规则：

- 画像摘要只归纳学生已保存答案，不推断敏感特征；
- 欢迎确认由服务端持久化；
- 修改欢迎语不会让已确认学生重复弹窗；
- 床位被分配、组队占用或临时占用时禁止修改类型；
- 房间容量继续以物理床位总数为准。

### 3.4 完整批次配置复制

新增接口：

```text
POST /api/v1/admin/batches/{batchId}/copy
```

管理员从批次列表点击“复制配置”，重新填写批次编码、名称、开始时间、结束时间和原因。系统在一个MySQL事务中创建草稿副本。

复制内容：

- 问卷版本；
- 匹配方案精确修订；
- 床位保留、续期、组队和随机推荐规则；
- 未选学生处理策略和规则版本；
- 楼栋、房间和床位开放范围。

不复制内容：

- 学生资格；
- 活动学生锁；
- 队伍、邀请和成员；
- Redis临时占用；
- 正式分配、分配历史和分配运行；
- 原批次状态、发布时间和完成时间。

复制规则：

- 除`CANCELLED`外的批次均可作为来源；
- 新批次编码必须唯一；
- 开始时间必须早于结束时间；
- 新批次固定为`DRAFT`；
- 源批次问卷、匹配方案和开放范围必须完整；
- 范围中的楼栋、房间和床位必须可用；
- 发现异常资源时整体拒绝，不静默跳过；
- 成功后记录`BATCH_COPY`审计。

## 7. 下一子项目

下一项为“规则模板与复杂组队异常处理”。推荐实施顺序：

1. 将批次中的组队、保留、随机推荐和未选处理规则抽象为可版本化规则模板；
2. 创建批次或复制批次时可选择精确模板修订；
3. 对邀请过期、重复邀请、成员跨批次、成员已有分配、成员退出和组长失效提供稳定处理规则；
4. 对锁定小组的成员变化、整体占用失败和确认失败给出可恢复状态；
5. 保持队伍编号和内部模板版本不在学生端展示；
6. 所有异常处理必须确定性、事务化、可审计并具备真实接口测试。
